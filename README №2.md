## 2. Юниты и их характеристики

### 2.1. Общий класс `Unit`

`Unit` - абстрактный базовый класс. Он хранит здоровье, броню, атаку, координаты, идентификатор, очки передвижения и временные бонусы. Общие операции реализованы в одном месте: получение урона, лечение, перемещение, проверка жизни и расчёт атаки.

Конкретный класс обязан предоставить свой тип и способ клонирования:

```cpp
class Unit : public IObservable {
public:
    virtual std::unique_ptr<Unit> clone() const = 0;
    virtual UnitType getType() const = 0;

    void takeDamage(int rawDamage, int defenseBonus = 0);
    bool isAlive() const;
};
```

`clone()` нужен для глубокого копирования игрового поля. `getType()` позволяет определить вид юнита через указатель на базовый класс, не зная его конкретного типа заранее.

### 2.2. Иерархия юнитов

В программе реализовано пять групп, по два вида в каждой:

| Группа | Виды |
|---|---|
| Пехота (`Infantry`) | `Swordsman`, `Spearman` |
| Лучники (`Archer`) | `LightArcher`, `HeavyArcher` |
| Конница (`Cavalry`) | `Cataphract`, `HorseArcher` |
| Маги (`Mage`) | `FireMage`, `IceMage` |
| Летающие (`FlyingUnit`) | `Gryphon`, `Wyvern` |

Все десять видов перечислены в `UnitType`:

```cpp
enum class UnitType {
    Swordsman, Spearman, LightArcher, HeavyArcher,
    Cataphract, HorseArcher, FireMage, IceMage,
    Gryphon, Wyvern
};
```

Дополнительные свойства вынесены в соответствующие классы: лучники имеют дальность атаки, маги - ману. Летающие юниты выделены отдельно, чтобы правила карты могли учитывать способность летать.

### 2.3. `UnitTypeInfo`

Параметры вида юнита не дублируются в логике поля. `UnitTypeInfo` хранит максимальное здоровье, базовую атаку, скорость, стоимость и тип. Метод `getInfo()` возвращает общую неизменяемую запись для выбранного вида.

```cpp
const UnitTypeInfo& info = *UnitTypeInfo::getInfo(UnitType::Swordsman);
```

За счёт этого характеристики можно получить из одного места, а экземпляры юнитов хранят ссылку на общий набор параметров.

### 2.4. Классы характеристик

- `Health` хранит здоровье и не позволяет уменьшить его ниже нуля.
- `Armor` уменьшает входящий урон.
- `Attack` рассчитывает наносимый урон с учётом брони цели.

Дополнительный бонус защиты клетки передаётся при получении урона отдельно от собственной брони юнита.

## 3. Фабрика создания юнитов

Создание конкретных юнитов вынесено из игрового поля в фабрики. Базовый интерфейс `UnitFactory` объявляет метод `createUnit()`, а конкретная фабрика выбирает класс по `UnitType`.

Используются пять фабрик: `InfantryFactory`, `ArcherFactory`, `CavalryFactory`, `MageFactory` и `FlyingFactory`.

Интерфейс фабрики и один из вариантов создания:

```cpp
virtual std::unique_ptr<Unit> createUnit(UnitType type, int x, int y) const = 0;

case UnitType::Swordsman:
    return std::make_unique<Swordsman>(x, y);
```

Вызвавшая код часть получает `std::unique_ptr<Unit>` и работает с базовым интерфейсом. Ей не нужно самостоятельно вызывать конструктор `Swordsman`, `FireMage` или другого конкретного класса.

**Почему выбран фабричный метод:** создание разделено по группам юнитов, а код, который использует базовый класс `Unit`, не зависит от конкретных конструкторов. Для добавления нового вида достаточно реализовать сам класс и подключить его создание в соответствующую фабрику.

## 4. Игровое поле (`GameField`)

Поле хранит сетку клеток в `std::vector<std::unique_ptr<Unit>>`. Пустая клетка содержит `nullptr`, занятая - владеющий указатель на юнита.

Основные операции:

- добавить юнита по координатам или через фабрику;
- удалить юнита по координатам или индексу клетки;
- переместить юнита;
- получить юнита в заданной клетке;
- проверить размер и лимит, очистить поле.

Перед добавлением проверяются границы, занятость клетки и максимальное количество юнитов.

### 4.1. Копирование и перемещение

Для `GameField` реализовано правило пяти: деструктор, копирующий и перемещающий конструкторы, а также оба оператора присваивания.

При копировании нельзя просто скопировать `unique_ptr`: это привело бы к совместному владению одними и теми же объектами. Поэтому поле вызывает `clone()` для каждого существующего юнита. Копия получает собственные экземпляры.

При перемещении передаётся внутренний вектор, а исходный объект приводится в пустое состояние.

### 4.2. Итератор

`GameFieldIteratorT` оборачивает итератор вектора и пропускает пустые клетки. Есть обычная и константная версии.

```cpp
for (Unit& unit : game.field()) {
    // Обрабатывается только существующий юнит
}
```

Внутри `skipEmpty()` итератор двигается дальше, пока не встретит занятую клетку. Такой обход используется, например, для массового урона, вывода списка и удаления погибших юнитов.

Глубокое копирование поля выполняется через `clone()`:

```cpp
for (const auto& cell : other.cells_) {
    cells_.push_back(cell ? cell->clone() : nullptr);
}
```

Таким образом, копия хранит отдельные экземпляры юнитов и не меняет оригинал при получении ими урона.

## 5. Контроллер игры и база

### 5.1. `GameController`

`GameController` связывает основные части программы. Внутри него находятся:

- `GameField` - юниты на карте;
- `TerrainMap` - карта местности и нейтральные объекты;
- `Base` - база игрока.

Контроллер проверяет игровые условия и выполняет действия: создание и перемещение юнитов, атаки, урон, завершение хода, взаимодействие с объектами и удаление погибших.

Важно различать два способа создания юнитов:

- `createUnit()` создаёт юнита через базу: проверяются стоимость, ресурсы и лимит базы;
- `createFreeUnit()` / `addFreeUnit()` добавляют юнита напрямую на поле. Этот вариант используется в демонстрациях и не расходует ресурсы базы.

Обычный ход `moveUnit()` разрешает перейти только в соседнюю клетку. При этом проверяются занятость, границы, проходимость местности и оставшиеся очки движения. Общая последовательность проверки выглядит так:

```cpp
if (!terrain.isPassable(unit->getType())) {
    return "Местность непроходима";
}
if (!unit->spendMovePoints(cost)) {
    return "Недостаточно очков движения";
}
field_.moveUnit(fromX, fromY, toX, toY);
```

`teleportUnit()` используется отдельно для перемещения без расходования очков движения, но также проверяет карту и целевую клетку.

### 5.2. База (`Base`)

База имеет координаты, здоровье, уровень защиты, запас ресурсов и ограничение на количество подконтрольных юнитов. Она создаёт юнитов за ресурсы, хранит список действующих юнитов и историю погибших.

В начале игры база располагается в левом верхнем углу карты. Её параметры и лимит юнитов задаются при создании игры.

### 5.3. Паттерн Observer

`Unit` реализует интерфейс наблюдаемого объекта (`IObservable`). База подписывается на события принадлежащих ей юнитов. Когда такой юнит погибает, база получает уведомление, обновляет количество действующих юнитов и добавляет запись в историю.

Это позволяет базе отслеживать состояние юнитов без постоянного опроса каждого из них. Погибший объект при этом может оставаться на игровом поле до отдельного вызова удаления погибших.

## 6. Карта и ландшафт

### 6.1. `TerrainMap`

Карта имеет те же ширину и высоту, что и игровое поле. В каждой клетке находится объект местности, а нейтральные объекты хранятся отдельно. При генерации типы местности распределяются случайным образом.

`Terrain` - абстрактный интерфейс. Для каждого типа местности задаются проходимость, модификатор скорости, бонус защиты, вероятность пропустить ход, символ и название.

| Местность | Правила |
|---|---|
| Равнина (`Plains`) | Проходима для всех, не меняет скорость и защиту |
| Лес (`Forest`) | Не пропускает тяжёлых юнитов; замедляет пехоту и даёт бонус защиты |
| Болото (`Swamp`) | Замедляет юнитов и может заставить их пропустить ход |
| Горы (`Mountains`) | Проходимы только для летающих юнитов |

Стоимость перемещения зависит от модификатора скорости клетки. Поэтому один и тот же переход может требовать разное количество очков движения для разных юнитов.

### 6.2. Паттерн Proxy - `TerrainProxy`

`TerrainProxy` оборачивает настоящий объект местности и предоставляет тот же интерфейс `Terrain`. Карта хранит именно прокси, а тот обращается к реальному объекту.

```cpp
cells_[y][x] = std::make_unique<TerrainProxy>(std::move(real));
```

В этой реализации прокси отдельно обрабатывает летающих юнитов: они могут проходить над препятствиями, не получают наземные модификаторы скорости и защиты и не рискуют застрять в болоте. Попытки пройти через непроходимую клетку записываются в журнал.

## 7. Нейтральные объекты и паттерн Strategy

Нейтральные объекты размещаются на карте независимо от юнитов. У каждого объекта есть координаты, символ, название и действие при взаимодействии.

| Объект | Результат взаимодействия |
|---|---|
| Сундук (`TreasureChest`) | Добавляет ресурсы базе |
| Ловушка (`Trap`) | Наносит юниту урон |
| Алтарь (`Altar`) | Даёт бонус, зависящий от класса юнита |
| Источник энергии (`EnergySource`) | Полностью восстанавливает здоровье |

За само действие отвечает стратегия `IInteractionStrategy`. Конкретные стратегии реализуют отдельные эффекты: урон, ресурсы, лечение, увеличение атаки, дальности или маны.

```cpp
class IInteractionStrategy {
public:
    virtual std::string apply(Unit& unit) = 0;
};
```

`Altar` выбирает стратегию по типу посетившего его юнита: маг получает ману, лучник — временное увеличение дальности, остальные юниты — временный бонус атаки. Поэтому один объект может вести себя по-разному в зависимости от того, кто с ним взаимодействует.

В программе также перегружены операторы для наглядной записи взаимодействий: `+` - сундук, `-` - ловушка, `*` - алтарь, `/` - источник энергии. Например:

```cpp
unit + chest;  // получить ресурсы
unit - trap;   // получить урон
unit * altar;  // получить усиление
unit / source; // восстановить здоровье
```

Это специальные операции над объектами, а не арифметические вычисления. Для обхода непустых клеток с объектами используется отдельный `ObjectIterator`.

## 8. Журнал событий

`Logger` предоставляет статические методы для добавления записи и получения списка сообщений. Журнал отображается в меню, а записи также сохраняются в файл `game.log`.

В него попадают важные события: создание юнитов, действия с местностью, взаимодействия и завершение хода.

## 9. Консольный интерфейс

Файл `Osobo Opasniy Prestupnik #1.cpp` содержит `main()`, меню, обработку пользовательского ввода, отрисовку карты и демонстрационные сценарии.

Меню разделено на две страницы:

- **ЛР 1 — игровое поле:** создание и удаление юнитов, перемещение, информация, атака, массовый урон, список юнитов и три боевых сценария;
- **ЛР 2 — база и карта:** создание юнитов на базе, перемещение по ландшафту, завершение хода, проверка Proxy, урон и информация о базе, журнал, сценарии и автотесты.

На карте используются условные обозначения:

| Символы | Значение |
|---|---|
| `*`, `&`, `~`, `^` | Равнина, лес, болото, горы |
| `B`, `C`, `T`, `P`, `R` | База, сундук, ловушка, алтарь, источник энергии |
| `M`, `S`, `L`, `H`, `K`, `E`, `F`, `I`, `G`, `W` | Десять видов юнитов |

Погибший юнит отображается строчной буквой. Цветной вывод включается для поддерживаемых терминалов.

## 10. Демонстрационные сценарии и проверка

В программе предусмотрено семь сценариев:

1. **Ядерный удар** - две армии размещаются на поле и уничтожаются одним массовым ударом.
2. **Местная междоусобица** - катафракты сражаются с пехотой и лучниками; показывается автоматическое сближение и ход боя.
3. **Типовая мировая война** - на поле размещаются три армии: пехота, лучники и конница; одна из армий случайным образом назначается победителем сценария.
4. **База и юниты** - демонстрируется создание юнитов, расход ресурсов и ограничение вместимости базы.
5. **Ландшафт и Proxy** - проверяется проходимость леса, болота и гор для разных типов юнитов.
6. **Нейтральные объекты** - демонстрируются сундук, ловушка, алтарь и источник энергии.
7. **Observer** - база получает уведомления о гибели юнитов, обновляет счётчик и сохраняет историю.

Пункт **«Автотесты»** запускает проверки основных механизмов: правил ландшафта, создания юнитов и лимита базы, уведомлений Observer, эффектов нейтральных объектов, итератора объектов, глубокого копирования и перемещения игрового поля. Результат каждой проверки выводится отдельно:

```cpp
check(report, failed, "Лимит юнитов базы соблюдается", condition);
```
